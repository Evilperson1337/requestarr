# Security Baseline

- OIDC required after first-run setup; Keycloak compatibility covered by integration tests.
- Authorization enforced server-side for every mutating/admin endpoint.
- Bootstrap setup token is temporary, high entropy, and invalidated after completion.
- Never expose provider/library secrets after storage; UI returns redacted configuration state.
- Encrypt secret material at rest or use a deployment secret provider before production release.
- CSRF protections appropriate to session/cookie architecture; SameSite/Secure/HttpOnly cookies.
- OIDC state, nonce, PKCE, issuer/audience validation and strict redirect URL policy.
- SSRF controls for administrator-supplied integration URLs: allow explicit schemes, reject unsafe URL forms, resolve/re-check destinations where practical, and document private-LAN requirements.
- Outbound HTTP clients have finite connect/TLS/header/body timeouts and maximum response sizes.
- Artwork/proxy behavior must not become an unrestricted URL fetcher.
- Sanitize logs. Authorization/cookie/token/secret values are always redacted.
- Audit request state changes, subscription changes, admin configuration changes, and setup completion.
- Database migrations and backups documented before stable release.
- Rate-limit URL resolution, authentication callbacks, setup validation, and notification test actions.
- Resumable setup reads require the short-lived setup session cookie. Setup mutations additionally require exact configured Origin and exactly `X-Requestarr-CSRF: 1`; no CORS/preflight support exists.
- Setup workflow persistence accepts only keyed session digests and strictly versioned server-produced drafts. It never stores raw cookies, bootstrap tokens, arbitrary request JSON, or secrets.
- OIDC setup discovery is revision-bound and secret-free. It uses complete-answer DNS policy, exact CIDR exceptions for internal destinations, checked-IP dial pinning with original TLS SNI, TLS 1.2+, no proxy, no redirects, strict bounded JSON, and durable per-session/global limits. External calls occur outside transactions and never during startup or routine state reads.
- Stored integration credentials use AES-256-GCM envelopes with fresh 12-byte nonces and associated data binding version, namespace, owner UUID, and secret name. Key IDs are domain-separated identifiers, not secrets or password verifiers.
- `REQUESTARR_ENCRYPTION_KEY` is independent 32-byte random deployment material in canonical unpadded base64url. Database/key backups are coupled. Existing encrypted rows make missing, invalid, or incompatible keys a fail-before-listen condition; V1 has one active key and no online rotation.
- Database-only compromise is in scope for at-rest protection. A compromised running process/host, memory inspection, or theft of both database and deployment key is not. Logs, errors, dumps, APIs, and audit data must not reveal plaintext/key material; future read APIs expose presence only.
- **Normal-auth migration gate:** `000011_normal_auth_foundation` may run only on a fresh or empty-user database. Earlier user rows lack issuer provenance, so the migration rejects any existing user and must never silently backfill, default, or guess an issuer.
- Future normal-auth persistence must atomically consume only unexpired, unconsumed login transactions and read only unrevoked, unexpired sessions; deletion/cleanup cannot establish authorization correctness. Runtime snapshots require typed validation before persistence. Auth audit payloads must be typed and allowlisted per event, not arbitrary JSON/maps or copied provider/runtime data, and must exclude tokens, cookies, credentials, claims, request bodies, and opaque artifact digests.
